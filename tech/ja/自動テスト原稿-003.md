# イエローカードを出されないために

# viMarkdown に組み込んだ話

## はじめに
現在、CommonMarkやGFM（GitHub Flavored Markdown）に準拠した、サクサク動くマークダウンエディタ「viMarkdown」を開発しています。リアルタイムプレビューやプレビュー内での直接編集をはじめ、CSVブロックやSVGブロックの表示、高度なdiff同期機能、そして本格的なvi/exキーバインドなど、開発者も快適に執筆できるための機能を盛り込んだエディタを目指しています。

開発ロードマップとしては、5月から始まった開発版（今ここ）に続き、8月にアルファ版、10月にベータ版、そして12月にはRC版およびStable版のリリースを予定しています。

現在はその目玉機能の1つである「viコマンド」を絶賛実装中なのですが、開発を進める中で大きな壁にぶつかりました。viコマンドを実行した際、その後のカーソル位置が１文字でもずれると、目の肥えた「Vimおじさん（熟練Vim使い）」たちは決して許してくれません。彼らに実用的な道具として認められるためには、カーソル位置を１文字の狂いもなく完全に制御する必要があるのです。
## なぜVimおじさんは１文字のずれも許してくれないのか
熟練のVim使い（いわゆるVimおじさん）にとって、カーソル移動は頭で考える「意識的な操作」ではなく、すでに指先が覚えている反射（マッスルメモリー）に近いものです。マウスへ手を持ち替えるなど論外で、移動先を認識した瞬間、意識することなく必要なviコマンドを打鍵しています。

そのため、コマンド実行後のカーソル位置が本来のviの仕様からたった１文字でもずれていると、それだけで思考を妨げる大きなノイズになります。

さらに厄介なのは、そのカーソル位置のずれに気づかないまま文字の挿入や削除といった次の操作を行ってしまうと、本来編集すべきではない場所を書き換えてしまい、期待した編集結果にならないことです。

だからこそ、Vim使いはカーソル位置の１文字のずれに極めて敏感です。これは単なるこだわりではなく、編集の正確性と作業効率を支える重要な前提条件なのです。
## なぜ自動テストが必要か
viのキーバインドは、コマンド数が多いだけでなく、それらを自由に組み合わせられることが最大の特徴です。具体的には、「operator（c, d, y, <, > など）」と「motion（h, j, k, l, Space, BS, w, W, e, E, b, B, 0, ^, $, f, F, t, T, ,, ;, /, ? など）」、さらに「count（繰り返し回数）」の3つの要素を組み合わせることで、膨大な数のキーパターンが生まれます。

前述の通り、カーソル位置が１文字でもずれた時点で、実用的なキーバインドとしては破綻してしまいます。そのため、あらゆるコマンドの組み合わせで期待通りに動作することが求められます。しかし、無数に存在するエッジケースを手動テストだけで網羅することは、現実的にはほぼ不可能です。

さらに、ある不具合を修正すると、その修正が思わぬ形で別のコマンドの組み合わせにデグレ（副作用）を引き起こす危険も常につきまといます。こうした問題を防ぎ、安心して機能追加やリファクタリングを進めるためにも、自動テストの導入は避けて通れない選択でした。

そこでviMarkdownでは、vi/exコマンドの入力・実行後のテキスト・カーソル位置を自動的に検証するテスト環境を構築しました。
## テストケース形式
自動テストを構築するにあたり、最もこだわったのがテストケースをどのような書式で記述するかという点です。本プロジェクトでは、保守性と記述のしやすさを重視し、プレーンテキスト上に特定の記号を配置するシンプルなDSL（ドメイン固有言語）形式を採用しました。

テストケースは、「テスト名」「初期状態のテキストおよびカーソル位置」「実行するvi/exコマンド」「期待される実行後のテキストおよびカーソル位置」を順番に記述するだけです。

カーソル位置は、エディタで最も重要な状態の一つであるため、太い縦罫線 ┃ で表現することにしました。また、ビジュアルモードなどの選択範囲は 《 と 》 で囲んで表します。

実際のテストケースを見てみましょう。例えば、カーソル位置から3単語を削除するコマンド（d3w）は、次のように記述します。

```text
Test: d3w (Delete 3 words)
Before:   ┃one two three four
Command:  d3w
Expected: ┃four
```

また、ビジュアルモードで単語末尾までを選択するコマンド（ve）のように、選択範囲を伴うテストも直感的に表現できます。

```text
Test: ve (Visual select to end of word)
Before:   ┃Hello world
Command:  ve
Expected: 《Hell┃o》 world
```

この記法では、テキスト・カーソル位置・選択範囲を一目で把握できます。そのため、人間が読み書きしやすいだけでなく、後述する生成AIによるテストケース生成に適した、認知負荷の低い形式です。
## 自動テストの仕組み
自動テストの実装は、できるだけシンプルで堅牢な構成を目指しました。

全体の流れは、定義されたすべてのテストケースを順番に実行し、それぞれについて以下の3つのステップを繰り返すだけです。

まず、テストケースに記述された初期状態（Before:）を読み込みます。プレーンテキスト中のカーソル（┃）や選択範囲（《 》）をパースし、テキスト・カーソル位置・選択範囲をエディタへそのまま復元します。

次に、その状態からテストケースで定義されたvi/exコマンドを実行します。コマンドが複数並んでいる場合は、記述された順番に1つずつ評価していきます。

最後に、コマンド実行後のテキスト・カーソル位置・選択範囲をエディタから取得し、期待値（Expected:）と１文字単位で比較します。テキストだけでなく、カーソル位置や選択範囲も完全に一致していることを確認し、わずかでも差異があればテスト失敗（Failed）として扱います。その際は、原因を特定しやすいよう、実際の結果と期待値の差分を含む詳細なエラーメッセージを出力します。
## 生成AIでテストケースを作る
viコマンドの組み合わせ爆発に対応するため、テストケースは基本的に生成AIに作成してもらっています。しかし、完全にAI任せにできるほど単純ではなく、実用的なテストを揃えるには、それなりの工夫と試行錯誤が必要でした。

例えば、単純に「h, j, k, l移動のテストケースを作って」と指示しただけでは、生成されるのは1マス移動のような基本的なケースばかりでした。viでは欠かせない「5k」や「10j」のような繰り返し回数（count）を伴う操作や、その境界条件に関するテストがすっぽり抜け落ちてしまいました。

そのため、意味のあるテストを網羅してもらうには、「countを考慮したテストも必ず含めること」のように、人間側が意図を明確に伝え、プロンプトを調整していくことが欠かせませんでした。

また、本プロジェクトでは1つのAIモデルに依存せず、複数のAIの得意分野を組み合わせる協調アプローチを採用しています。具体的には、まずGemini先生に大量のテストケース案を生成してもらい、それをチャッピー先生やClaude先生にレビューさせ、不足しているエッジケースの追加や、誤った期待値・テスト記述の修正を行っています。いわば、AI同士による「相互査読」のような開発スタイルです。

さらに、テストが失敗した際の原因分析にも生成AIを活用しています。失敗ログをAIに渡し、仕様との食い違いがないかを検証してもらうのですが、原因が常にC++側の実装バグとは限りません。AIが生成したテストケースの期待値（Expected:）が誤っていることもあれば、自作したテストシステム自体に不具合が潜んでいることもあります。

つまり、失敗の原因が「vi/exの実装」「テストケース」「テストシステム」のどこにあるのかを、AIと対話しながら切り分けていくことになります。この「AIにテストを書いてもらい、そのAIと一緒にデバッグする」という開発スタイルは、生成AI時代ならではの、とても新鮮で楽しい体験になっています。
## テスト結果メッセージ
開発効率を高めるため、テスト結果を出力するコンソールメッセージの「見やすさ」にもこだわりました。

まず、すべてのテストが正常にパスした場合は、余計な情報を表示せず、テスト実行中は現在実行中のコマンドカテゴリ（移動、削除、インデントなど）とテストの進捗のみを表示し、最後に実行件数と成功率をまとめて表示します。大量のテストを何度も実行する開発では、必要な情報だけを簡潔に表示することが重要です。

```
Test vi commands...

Move forward word (w) - Basic spacing: ...
Move forward word (w) - Across lines and empty lines: ....
Move forward word (w) - Punctuation boundaries: .....
Move forward multiple words (num w) - Basic counts: ...
Move forward word (w) - Japanese word classes: .....
Move forward word (w) - Japanese mixed with alphanumeric and spaces: ......

Total: 0 failed / 26 tested. (Success:100.0%)
```

一方、テストが失敗（アサーションエラー）した場合は、原因を素早く特定できるよう、初期状態（Before:）、実行したviコマンド（Commands:）、期待値（Expected:）、実際の結果（Actual:）の4つを縦に並べて表示します。

例えば、次のような失敗メッセージが出力されます。

```
Move to end of line ($) and EOL memory: .......
[FAILED] Test: dw (Delete word)
Before:   h┃ello world
Commands: dw
Expected: h┃world
Actual:   h┃llo world
```

この例では、本来削除されるべき「ello」が残ってしまっており、期待値と実際の結果を見比べるだけで、不具合の内容を直感的に把握できます。

このような出力形式にしたことで、テストケース定義を開き直すことなく、コンソールログだけで不具合の状況を確認できるようになりました。どの操作で、どの文字列が期待通りに編集されず、カーソル位置がどのようにずれたのかをすぐに特定できるため、デバッグの初動を大幅に短縮できています。
## 得られた効果
自動テストを導入したことで、開発スピードと品質の両面で大きな効果を実感しています。

最も分かりやすい効果は、バグを早期に発見できるようになったことです。viのように複雑なキーバインドを実装するエディタでは、わずか1行のコード変更が、思いもよらないカーソル移動や選択範囲の挙動に影響を与えることがあります。しかし現在では、コードを変更したらテストを実行するだけで、どのコマンドで何が壊れたのかをすぐに把握できます。その結果、不具合を長期間見逃したまま開発を進めてしまい、後になって原因調査に多くの時間を費やすことが大幅に減りました。

もう一つの大きな効果は、安心してリファクタリングを行えるようになったことです。C++の複雑なロジックを整理したり、肥大化した関数を分割したりする際には、「どこか別の動作を壊してしまうのではないか」という不安が常につきまといます。しかし現在では、大胆にコードを書き換えた後でも、テストを実行して Success:100.0% を確認できれば、既存の挙動が維持されていることを高い確信を持って判断できます。

自動テストは、品質を保証する仕組みであると同時に、開発者が安心してコードを改善し続けるための「命綱」でもあります。この安心感が、継続的な機能追加やリファクタリングを支える大きな原動力になっています。

Vimおじさんに「1文字のずれ」を指摘されない品質を維持するためにも、自動テストは今やviMarkdown開発に欠かせない存在となっています。
## まとめ
viの完全互換を目指す道のりは、想像以上に難易度が高く、多くの開発コストを要する挑戦です。しかし、強力な自動テストの基盤があるからこそ、迷うことなく自信を持って実装を進められています。自動テストが問題を検出してくれるおかげで、目の肥えたVim使いの方々に「イエローカード」を提示される不安が劇的に減少しました。

このテスト自体は数秒で完了するため、開発中はコーディングの合間に何度でも気軽に実行することができます。現在も日々新たなテストケースを追加し、網羅率を広げながら、vi互換性の精度を着実に高めている最中です。開発ロードマップに掲げたベータ版リリース（10月予定）のタイミングまでに、蓄積されたすべてのテスト失敗を0件にし、安心して実務に投入できる品質をお届けすることを目標に掲げています。
