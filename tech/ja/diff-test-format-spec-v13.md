# diff 自動テスト書式 拡張仕様（2026-11-15 改訂版）

## 1. 背景と目的

- 現行の diff 固定テスト（`AutoTest.cpp` の `g_diffTestCase`）は有効ケース2件・計4チェックのみ。
- 判定関数 `test_diff_line` は「各行がダミー行かどうか」しか見ておらず、行のテキスト内容、行の状態（変更・追加の区別）、変更行内の単語強調範囲、相手への反映操作は、すべて未検証。
- 本仕様は、ブロック単位・単語単位の反映操作と、変更行の単語強調までテストケースで書けるようにするための、書式の拡張案である。

## 2. ケース全体の構造（現行を踏襲）

1ケースは文字列リストで、次の並びとする。

```
{ "テスト名",
  左テキスト, 右テキスト,            // 初期文書 兼 最初の期待値
  アクション, 左期待値, 右期待値,     // 以後、この3つ組の繰り返し
  ...
}
```

- テキストは行ごとの文字列の連結。各行の先頭1文字が行マーカー。
  - `=` 不変行
  - `+` 追加行（相手側はダミー行）
  - `!` 変更行
  - `-` ダミー行（その側には存在しない行）
- ダミー行は、初期ロード時には実文書に入れない（セットアップでは読み飛ばす）。ただし `do_diff()` の実行後は、diff 表示上の対応位置にダミー行を表すブロックが生成される。ダミー行は実文書の内容（ファイルに保存されるテキスト）には含まれない。
- 行番号は、その側の期待値テキストの行を1から数えたもの（ダミー行も含めて数える）。左右の期待値は行数が一致し、差分ブロックの先頭は左右で同じ行位置に揃うため、ブロックの指定はこの行番号で一意に定まる。アプリの行番号表示（ダミー行には番号が出ない）とは一致しないが、ハーネスの座標は期待値テキストを基準とする。
- 各ステップでは、アクション実行後に `do_diff()` を再実行し、左右の期待値と照合する（現行のステップループ通り）。
- 用語：本書で「行」は QTextBlock（1行）を指す。「差分ブロック」は差分のまとまり（hunk）を指し、`=` でない行の連続を1つの差分ブロックとする（`+` の直後に `!` が続く場合も、連続していれば同じブロック）。

## 3. 期待値テキストの記法：単語強調と欠落位置

- 変更行の単語強調範囲は、行内に `《` `》` で囲んで表す。
  - 例：`!aaa 《bbb》 ccc`（bbb だけが単語差分）
  - 複数範囲も可：`!《aaa》 bbb 《ccc》`
  - 空白だけの範囲も可：`《 》`。単語と空白が別々の範囲なら `《bbb》《 》` と隣接して書く。
  - 隣接する範囲は統合せず、別々の範囲として照合する（実装でも単語と後続空白は別々の範囲）。
- 相手側にだけある単語の欠落位置（gaps）は、空の `《》` で表す。
  - 例：`!aaa《》bbb`（aaa と bbb の間に欠落位置がある）
  - 実在の強調範囲は最低1文字（トークンは空でない）ため、空の `《》` は位置だけの意味で一意に読める。
  - カーソル位置を表す縦線記号は、意味が衝突するため使わない。
- `《` と `》` はこの書式の予約記号であり、テストデータの実テキストには使用できない。エスケープは用意しない。
- 照合方法：期待値から `《》` を取り除きながら（開始位置, 長さ）の列に変換し、その行の `DiffBlockUserData.ranges` と照合する。空の `《》` は `DiffBlockUserData.gaps` と照合する。
- `!` 行は常に照合する。`《》` が無い `!` 行は、「強調範囲・欠落位置とも空であること」を期待する意味になる（照合のスキップはしない）。既存ケース2件には、実際の範囲に合わせて `《》` を追記する。
- `ranges` / `gaps` は行ごとのローカル座標である（複数行にまたがる通しオフセットではない）。期待値も行単位でそのまま照合できる。内部的には QString のインデックス（UTF-16 コードユニット、0起点）であり、変換はハーネス側で行う。
- 範囲が行の末尾を越える既知の癖（行末の空白＋改行が1トークンになる場合）があるため、照合時は**実測側にだけ**、描画側と同じ規則（行の長さで切り取る）でクランプを適用する。期待値側の記法では改行を含む範囲を書けないためである。クランプ処理の関数自体の共通化は第2段階（7節）で行い、第1段階ではチェッカ側に同じ規則を書く（1行の上限処理であり、単語単位のロジック複写とは別扱いとする）。なお、この癖そのものは未起票であり、別途 SPR 化する候補とする（SPR 化すれば、将来癖を直したときに期待値を変えずに済む）。

## 4. アクション書式

### 4.1 対象の指定

- 編集系アクション（4.2）では、アクション文字列の先頭で、操作対象の文書を `L`（左、デフォルトで省略可）/ `R`（右）で指定する。
- 従来の `>` / `<` による対象指定は廃止する。既存ケースの `">x"`（右側で1文字削除）は `"R@1:1x"` と書き換える（`@` の必須化については 4.2）。
- 反映系アクション（4.3）には `L` / `R` を付けない。矢印自体が左右（反映の方向）を表すためである。`R>>2` のような併用は誤りとして扱う（4.4）。

### 4.2 編集系アクション

- 編集位置の指定：`x` と `i` では、編集コマンドの接頭辞として `@行:カラム` を付けることが**必須**である。省略した場合は誤りとして扱う（4.4）。理由：ステップごとに `do_diff()` がダミー行を挿入・削除するため、暗黙のカーソル位置は行がずれて意味が変わり得る。ケースを暗黙のカーソル位置に依存させない。
  - 例：`@2:3x` ＝ 2行目3文字目にカーソルを置いて1文字削除
  - 例：`R@2:3iabc\x1b` ＝ 右側の2行目3文字目から `abc` を挿入（`L` / `R` と併用できる。並びは対象指定 → `@` → 編集コマンド）
  - `@` は `x` と `i` 専用の接頭辞である。`d` や `J`、`u`、`U` に付けた場合は誤りとして扱う（4.4）。
  - 行番号は期待値テキストの行（ダミー行込み）、カラムは「何文字目か」（単語反映と同じ数え方）。「1文字」は Unicode コードポイント単位とし、結合文字や ZWJ も独立した1文字と数える（書記素クラスタ単位にはしない）。カラムは「その行の文字数＋1」（行末位置）まで指定できる。
- `x`：カーソル位置の1文字削除（現行通り）。行末位置（文字数＋1）では削除できる文字が無いので誤りとして扱う（4.4）。行の連結はしない。
- `i` ＋ 文字列 ＋ `\x1b`：文字列挿入（現行通り）。`i` の後に続く文字列を、0x1B（C++ リテラルでは `\x1b` と書く）まで挿入する。終端の 0x1B は省略可能で、省略した場合は後に続く文字列をすべて挿入する（現行ハーネスの動作）。
- `d` ＋ 行番号：その行を削除する。例：`d2` で2行目を消す。
- `J` ＋ 行番号：その行の末尾の改行を消して、次の行と連結する。例：`J2` で2行目と3行目を連結する。空白の挿入や次行の字下げ除去といった vi の `J` の作法は入れず、単純な改行除去とする。最終行への `J` は誤りとして扱う（4.4）。
- `u`：undo。`U`：redo（アプリの redo キーは `U` であり、それに合わせる）。`Ru` のように対象側を指定できる。反映操作は1回の undo で丸ごと戻るはずの操作であり、その検証に使う。反映の undo / redo は**反映先の文書**に対して行う（例：`>>2` の後は `Ru`、`<<2` の後は `Lu`）。
- 行番号は、その側の期待値テキストの行を1から数えたもの（ダミー行も含めて数える。4.3 の反映系と同じ数え方）。
- 行番号・カラムなどの座標は、すべて**そのアクション実行直前の状態**（1つ前のステップの結果）を基準とする。ステップごとに `do_diff()` が再実行され表示が変わるため、`d2` の後に書く `>>3` は、削除後の表示の3行目を指す。
- ケースは暗黙のカーソル位置に依存しない（`x` と `i` は `@` で位置を明示する）。反映や undo / redo の後にカーソルがどこにあるかは、ケースの意味に影響しない。

### 4.3 反映系アクション

画面上の操作（行番号エリアの ≪ ≫ マーカー、右ボタンメニューの「相手に反映」）に対応する。

- ブロック反映：`>>` ＋ 行番号 / `<<` ＋ 行番号
  - 例：`>>2` ＝ 左文書の2行目が先頭の差分ブロックを右文書へ反映（画面の ≫ クリック相当）
  - 例：`<<3` ＝ 右文書の3行目が先頭の差分ブロックを左文書へ反映（画面の ≪ クリック相当）
  - 行番号は、その側の期待値テキストの行を1から数えたもの（ダミー行込み）。指定するのは差分ブロックの先頭行（アプリのクリック条件と同じ）。ブロックの先頭は左右で同じ行位置に揃っているため、どちらの側から数えても同じ行番号になる。
  - **反映元が全部ダミーのブロックも有効な操作である**。相手側にだけ行があるブロックで、ダミー側から反映すると「相手の追加行を削除する」反映になる。この場合、先頭行はダミー行になるが、そのまま行番号で指定できる。
- 単語反映：`>` ＋ 行番号 ＋ `:` ＋ カラム / `<` ＋ 行番号 ＋ `:` ＋ カラム
  - 例：`>2:3` ＝ 左文書の2行目3文字目にある単語を右文書へ反映
  - 例：`<2:3` ＝ 右文書の2行目3文字目にある単語を左文書へ反映
  - カラムは「その行の何文字目か」で数える（1始まり）。基準は、行マーカーと `《》` を除いた素の行文字列。「1文字」は Unicode コードポイント単位とし、全角文字も1文字、サロゲートペアも1文字、結合文字や ZWJ も独立した1文字と数える（表示幅や UTF-16 コードユニット数、書記素クラスタ単位では数えない）。QString インデックスへの変換はハーネス側で行う。その位置を右クリックする操作と等価な指定とする。行末位置（文字数＋1）には文字が無いので、単語反映では誤りとして扱う（4.4）。
  - 「単語」の単位はアプリの実物と同じ（トークン＋後続の半角空白）。単語を指した場合は、反映される範囲が後続の半角空白まで広がる。カラムが空白の上にある場合は、その位置に単語が無いので誤りとして扱う（4.4）。
- 単語の「不在」の反映（相手だけにある単語を、欠落位置を指定して消す操作）は、アプリに存在しないため、記法も用意しない。相手だけにある単語を消したい場合はブロック反映を使う。

### 4.4 不正な指定の扱い

- 次のような指定は、すべてテストケースのバグとして、ハーネスはエラーメッセージ（テスト名・アクション・指定箇所・理由）を出力し、そのケースを失敗とする。後続のステップは実行しない。
    - 反映で、差分ブロックの先頭でない行が指定された場合
    - 単語反映で、カラムが差分単語の上に無い場合
    - 存在しない行番号が指定された場合（期待値テキストの行数を超える番号）
    - 行削除・`J`・`@`・単語反映で、ダミー行が指定された場合（ブロック反映でダミー行が先頭の場合は有効な操作であり、除く）
    - `@行:カラム` で、その行の文字数＋1を超えるカラムが指定された場合
    - 行末位置（文字数＋1）で `x` が実行された場合
    - 最終行に対して `J` が実行された場合
    - `@` が `x`・`i` 以外のアクションに付けられた場合
    - `x`・`i` に `@行:カラム` が付いていない場合
    - 反映系アクションに `L` / `R` が併用された場合
    - どの書式にも合わないアクション文字列（旧書式の `">x"` など。移行時に黙って通過させないため、明示的にエラーとする）
- その操作自体は実行しない。代替解釈も行わない（たとえば、指定カラムに単語が無い場合にブロック単位の反映へ読み替える、といったことはしない）。
- 理由：黙って別の意味に解釈したり、何もせず素通りさせたりすると、テストケースのバグが見えなくなるため。

## 5. 判定（チェッカ）の拡張

現行の「ダミーかどうかだけ」から、次まで広げる。

- 行テキストそのものの照合（必須）。期待値のテキスト（行マーカーと `《》` を除いたもの）と、実際のブロックのテキストを比較する。
- 行の状態の照合：`=` / `+` / `!` / `-` が実際の diff 状態と一致すること。
- 単語強調範囲と欠落位置の照合（3節の通り）。
- 期待値同士の整合性チェック（ケース実行前の事前検証）：
  - 左右の期待値の行数が一致すること
  - `=` 行同士は本文が同一であること
  - 行マーカーの対応が双方向に成り立つこと（`+` の反対側は `-`、`-` の反対側は `+`、`!` の反対側は `!`、`=` の反対側は `=`）
  - `-` 行の本文が空であり、`《》` も無いこと
  - `=` 行と `+` 行に `《》` が無いこと（単語差分は変更行のペアにだけ計算されるため）
  - 空でない強調範囲の長さが1以上であり、範囲と欠落位置がそれぞれ出現順（昇順）に並んでいること
  - `!` ペアの本文が左右で異なること（同一なら `=` のはず）
  - `!` ペアの左右から、強調範囲と欠落位置をすべて取り除いた残りの文字列が同一であること（共通部分は左右で一致するはず。末尾の癖（3節）に関わる場合は例外があり得る）
  - `!` ペアの少なくとも片側に、強調範囲か欠落位置があること
  - 強調範囲同士が重なっていないこと、出現順に並んでいること
  - `《` と `》` が正しく対になっていること（入れ子・閉じ忘れ・開き忘れがないこと）
  - 空の `《》`（欠落位置）が同じ位置に連続して書かれていないこと
- 失敗時のダンプ：失敗したときは、実際の状態を同じ記法（行マーカーと `《》` つき）で出力する。期待値の修正が楽になり、ケースの自動生成にも使える。

## 6. 実装上の注意

- 単語単位の決定ロジック（単語＋後続空白への拡張など）は、実物のコンテキストメニュー処理とテストハーネスで共通の関数を呼ぶ形にする。ハーネス側に単位計算を複写すると、実物側が壊れてもテストが通ってしまう。
- 4.4 の判定（「差分ブロックの先頭行かどうか」「カラムが差分単語の上かどうか」）も、最終的には UI のハンドラと共通の関数にするか、ハーネスから UI と同じ入口を呼ぶ形にする。これらをハーネス側に複写して先行する場合は、暫定の複写であることを明記する（`applyDiffBlock` はクリック条件を通った後の処理なので、直接呼ぶだけでは「先頭でない行はアプリが無視する」挙動までは検証できない）。
- 反映操作の実体は既存の `applyDiffBlock`（差分ブロック）と `reflectWordToPeer`（単語）をそのまま使う。

## 7. 実装の順序

- 第1段階：記法・照合・事前検証・ダンプの拡張（3節・5節）に加えて、編集系アクション全部（4.2）とブロック反映（4.3）。いずれも AutoTest 側だけの変更で、製品コードに影響しないため先行できる。ただし 4.4 の先頭行判定は、共通化まではハーネス側の暫定複写とする（6節）。
- 第2段階：共通関数化（6節）。コンテキストメニュー処理などに触る製品コードの変更であり、RC のルール（ベータ以降は新規機能・大きな変更を入れない）に配慮し、RC1 の後に回すのが安全。
- 第3段階：単語反映（4.3）。第2段階に依存する。

## 8. 未決定・検討事項

- （解決済み）`《》` の無い `!` 行は、「強調・欠落とも空であるべき」と厳密に照合する（3節）。
- （解決済み）テストデータの実テキストに `《` `》` 自体は使用できない（予約記号）。エスケープは用意しない。必要になった段階で導入を再検討する。
- 末尾改行の有無の表現方法。案が2つある：(a) 現行書式（各行を `\n` 付きリテラルで連結）のまま、最終行の `\n` を書かなければ「末尾改行なし」とする。(b) 「全行（最終行も）末尾 `\n` あり」を既定とし、例外は後で考える。レビューでは (a) の推奨があった（実際の文書状態をそのまま表現できるため）。要判断。
- 強調範囲と欠落位置が同じ座標に存在できるかは、`DiffBlockUserData` の実際の仕様に合わせて決める。独自に制限しすぎると正常な diff 結果を不正扱いする恐れがあるため、事前検証の条件には含めていない。
- アプリ側が正当に何もしない操作（差分ブロックの先頭でない行のクリックなど）を検証したい場合に、「何も起きないことを期待する」ケースを明示的に書ける仕組みが要るか。候補：`?>>3` のように `?` 接頭辞を付けたアクションは、実行されずに状態が変わらないことを期待する形。
- 操作直後の状態と `do_diff()` 再実行後の状態の一致確認。各ステップで再実行して照合する現行方式に加え、操作直後（再実行前）の状態も確認すると、インクリメンタルな再計算経路の不変条件として強くなる。
- `#if 0` で無効化されている旧ケース（"Basic diff test" の左側削除版）の扱い。無効化の理由を git の履歴で確認し、アプリのバグで失敗していたなら SPR 化する。復活させる場合は `#if 0` ではなく「既知の失敗（SPR 番号付き）」として有効化する案がある。
